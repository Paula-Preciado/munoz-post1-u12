# ADR-001: Capas simples para persistencia; el seam de notificación ya cubre el próximo cambio conocido

- **Estado:** Aceptado — 2026-11-04
- **Autora:** Paula Andrea Muñoz Preciado (02230131025)
- **Alcance:** `aplicacion`, `infraestructura`, `procesamiento.notificacion`

## Contexto

Después de integrar Chain of Responsibility (RF1), Strategy (RF2) y Observer (RF3), hay que
decidir si el sistema debe pasar a **arquitectura Hexagonal completa**, con puertos e interfaces
intermedias para *todas* sus dependencias externas, o quedarse en **capas simples**.

El criterio de la Guía (sección 6.2) es que Hexagonal vale la pena *"en sistemas que sobrevivirán
3 años o más con cambios de infraestructura"*. Lo evalúo por separado para cada dependencia
externa, con datos del propio proyecto:

| Dependencia externa | ¿Cambio de infraestructura conocido? | Uso actual | ¿Se cumple el criterio hoy? |
|---|---|---|---|
| **Persistencia** (Spring Data JPA + H2) | **No.** No hay ningún plan de cambiar de motor de BD. JPA ya abstrae el motor: pasar de H2 a PostgreSQL es un cambio de `application.properties` y del driver, no de código. | 1 repositorio, 3 métodos (`save`, `findById`, `findByEmpleadoIdAndEstado`) y un solo consumidor (`SolicitudReembolsoService`) | **No** |
| **Notificación** (consola/log hoy) | **Sí.** Contabilidad anunció para el **próximo trimestre** una integración por API externa para el pago de las solicitudes aprobadas. | 3 observadores detrás de `ObservadorCambioEstado` | **Sí, y ya está cubierto** |

Alternativas evaluadas para la persistencia:

1. **Capas simples (actual):** el servicio depende de `RepositorioSolicitudesJpa`.
2. **Hexagonal:** interfaz de puerto `RepositorioSolicitudes` en `aplicacion`, más un adaptador
   `RepositorioSolicitudesJpaAdapter` en `infraestructura` que delega en Spring Data (y, si se
   quiere aislar del todo, una entidad JPA aparte con su *mapper* hacia `SolicitudReembolso`).

Alternativas evaluadas para la notificación:

1. **Sin cambios:** `ObservadorCambioEstado` ya es el *seam*.
2. **Puerto nuevo `PasarelaPagos`** con adaptador HTTP, creado desde hoy.
3. **Mensajería asíncrona** (cola/bus) entre el servicio y los observadores.

## Decisión

**Persistencia:** se mantienen **capas simples**. `SolicitudReembolsoService` sigue dependiendo
directamente de `RepositorioSolicitudesJpa`, sin un puerto intermedio. Hoy un puerto de
persistencia sería una abstracción especulativa (YAGNI): ningún caso de uso lo pide, tendría una
sola implementación y no pasa el test de explicabilidad ("¿para qué sirve esta interfaz?" →
"por si algún día cambiamos de base de datos", y ese día no está en ningún plan). El dominio ya
quedó libre de JPA gracias al mapeo `orm.xml`, que era lo único valioso que el puerto aportaba hoy.

**Notificación:** **no se cambia nada**. `ObservadorCambioEstado` ya desacopla el servicio de sus
interesados concretos. El próximo trimestre, `NotificadorContabilidad` reemplazará su
implementación interna (hoy un `println`) por la llamada a la API externa de pagos. Para eso no hay
que tocar `SolicitudReembolsoService` ni los otros observadores. El cliente HTTP que se necesite
se creará **cuando exista el contrato de la API**, no antes: hoy no se conocen ni el endpoint, ni
la autenticación, ni el formato del pago.

## Consecuencias

**Positivas**

- No se agregan interfaces, adaptadores ni *mappers* de persistencia sin un caso de uso real
  (se evitan unas 3 clases y su mantenimiento, sin ningún beneficio verificable hoy).
- El único cambio de infraestructura con fecha conocida (la integración de Contabilidad) ya tiene
  listo su punto de extensión y su prueba de regresión (`FlujoSolicitudReembolsoIntegracionTest`
  verifica que Contabilidad solo actúa en `APROBADA`).
- Las reglas ArchUnit (`ReglasArquitectura`) verifican los límites que **sí** existen
  (procesamiento sin persistencia ni web, controlador que solo usa aplicación y dominio) y no
  exigen puertos de persistencia, así que la decisión queda protegida en el pipeline.

**Negativas**

- Si en el futuro hay que cambiar de motor por algo que JPA no abstraiga (por ejemplo, un almacén
  documental), el puerto de persistencia habrá que **introducirlo retroactivamente**. Es una deuda
  técnica que se acepta de forma consciente y que está acotada: hoy hay un solo consumidor del
  repositorio.
- Un revisor que espere **simetría total** (puertos en todas las dependencias externas) puede
  leer la asimetría (seam en notificación, nada en persistencia) como una inconsistencia si no
  lee este ADR.
- La integración con la API de pagos será **síncrona** dentro de `cambiarEstado`. Si esa API es
  lenta o falla, afectará la respuesta del `PUT`. Se revisará cuando se conozca su SLA.

## Señales que harían revisar esta decisión

- Un plan aprobado de cambiar el motor de BD por uno que no sea relacional o que no soporte JPA.
- Un segundo consumidor de la persistencia con necesidades distintas (por ejemplo, un *batch*
  de reportes trimestrales con su propio modelo de lectura).
- Que la API de pagos de Contabilidad exija reintentos o procesamiento asíncrono: ahí sí se
  justificaría un puerto `PasarelaPagos` con su adaptador, o una cola.
